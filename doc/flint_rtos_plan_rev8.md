**Target Hardware (Initial):** ESP32-WROVER (Xtensa LX6, dual-core, internal SRAM + external PSRAM)  
**Secondary Target (Phase 8):** ARM32 Cortex-M4 (STM32F4 recommended)

>

## Vision

Flint is a preemptive real-time operating system for microcontrollers and bare-metal microprocessors. It strikes at the metal directly — no Linux compatibility layer, no POSIX pretense, no build system archaeology required.

**Flint is:**
- **Simpler than Zephyr or NuttX** — no Kconfig, no CMake, no weeks of onboarding
- **More capable than FreeRTOS** — clean TCP/IP, filesystem, bus drivers, and instrumentation as first-class features
- **Accessible to novices** — a wizard generates a working, buildable, flashable project in under two minutes
- **Honest about what it is** — a microkernel RTOS with isolated drivers, typed message queues, a three-layer driver model, and first-class debugging support

POSIX compatibility is explicitly not a goal. The `flint::` API is designed to fit embedded hardware directly. Developers familiar with FreeRTOS, ESP-IDF, or Arduino will feel productive immediately.

---

## Core Design Principles

1. **Preemptive, priority-based scheduling from day one.**
2. **Pure microkernel.** Drivers, filesystems, network stacks are isolated user-space tasks. The kernel contains only: scheduler, IPC/queue engine, MPU manager, DMA broker, interrupt router. Nothing else.
3. **Three-layer driver model.** Physical drivers, bus abstractions, and logical device drivers are formally separated. Adding a new device means writing only the logical layer. Adding a new MCU means writing only the physical layer. The two never need to know about each other.
4. **First-class debugging and instrumentation.** Zero cost in release builds. Full tracing, metrics, postmortem capture, and stack overflow detection available from the first line of kernel code.
5. **Typed message queues as the primary IPC primitive.**
6. **Declarative board manifest.** `board.rs` is the single source of truth. Generated by the wizard. Validated at compile time.
7. **Wizard-first onboarding.** `cargo generate` is the entry point for every new project.
8. **User-extensible driver workspace.** Every generated project includes pre-scaffolded folders and in-project templates for adding custom drivers at any layer. Adding a driver that isn't in the Flint core is as simple as copying a template and filling in the blanks — no external documentation required.
9. **Community driver convention.** Third-party drivers follow the same template and can be pulled directly via Cargo's Git dependency support. A curated community index lives in the Flint GitHub org as a single flat file — no registry infrastructure required.
10. **Additive phases.** Each phase produces a working, testable system.

## Three-Layer Driver Model

This is a first-class architectural pillar, not an implementation detail.

```
+--------------------------------------------------+
|  LAYER 3 — Logical Driver                        |
|  "What the device is and how to talk to it"      |
|  Examples: bme280, ssd1306, w5500, ds18b20       |
|  Compiled into: calling task (app or driver)     |
|  Knows: device registers, protocol, timing       |
|  Does not know: which bus, which pins, which MCU |
+--------------------------------------------------+
          ↕  flint::Bus trait (in-process call)
+--------------------------------------------------+
|  LAYER 2 — Bus Abstraction                       |
|  "How to move bytes"                             |
|  Examples: spi_bus, i2c_bus, uart_bus, can_bus   |
|  Compiled into: calling task (app or driver)     |
|  Knows: transfer protocol, speeds, framing       |
|  Does not know: which device, which MCU register |
+--------------------------------------------------+
          ↕  ONE IPC message (queue send/recv)
+--------------------------------------------------+
|  LAYER 1 — Physical Driver Task                  |
|  "The specific hardware that moves those bytes"  |
|  Examples: esp32_spi2, stm32f4_i2c1             |
|  Runs as: isolated user-space task               |
|  Knows: MCU register addresses, DMA setup        |
|  Does not know: what bus protocol, what device   |
+--------------------------------------------------+
```

### Critical design decision: one IPC hop, not three

Layer 3 (logical) and Layer 2 (bus abstraction) are **library crates**, not separate tasks. They compile directly into whatever context calls them — an application task, or a composite driver task. They are pure Rust with no privilege requirements and no hardware register access.

Only Layer 1 (physical driver) runs as an isolated task, because it is the only layer that requires:
- Direct access to memory-mapped peripheral registers
- Handling of hardware interrupts via the kernel's Interrupt Router
- DMA engine programming via the DMA Broker

The result is exactly **one IPC hop** per hardware operation — application context calls through Layer 3 and Layer 2 in-process, then sends a single typed queue message to the Layer 1 physical driver task. This is the same cost as FreeRTOS with a driver abstraction layer and is fast enough for any practical embedded workload.

```
App Task
  │  (Layer 3 + Layer 2 execute in-process — no IPC)
  │  bme280.read_temperature()
  │    → spi_bus.transfer(payload)
  │      → formats a PhysTransfer message
  │
  ├──── ONE queue message ────► Layer 1 Physical SPI Driver Task
  │                               programs registers, runs DMA,
  │                               sends result back
  ◄──── ONE queue message ─────┘
  │
  │  result returned to bme280.read_temperature() caller
```

### Layer boundary enforcement

The separation is enforced structurally by the Cargo dependency graph, not by convention:

- Layer 3 crates may only depend on `flint-api` (the `Bus` trait and `flint::log`/`flint::metric`). They cannot import `flint-arch-*` or any Layer 1 crate. This is a compile-time hard boundary.
- Layer 2 crates may only depend on `flint-api`. Same restriction.
- Layer 1 crates depend on `flint-api` and `flint-arch-<target>`. They are the only crates with access to physical register addresses and the DMA broker.

A logical driver that attempts to access hardware registers will fail to compile because the required crate is not in its dependency tree.

### What adding functionality looks like at each layer

**Adding a new device (BME280 sensor) — Layer 3:**
Write a library crate. ~50–200 lines. Uses only `flint::bus::*`. Compiles into the calling app. Never touch Layer 1 or 2 internals.

```rust
// drivers/logical/bme280/src/lib.rs
// This is the ENTIRE driver. No hardware knowledge required.
// This crate compiles into your application task — zero IPC overhead.
pub struct Bme280 {
    bus: flint::BusHandle,
}

impl Bme280 {
    pub fn new(bus: flint::BusHandle) -> Self { Self { bus } }

    pub fn read_temperature(&self) -> Result<f32, DriverError> {
        // This call formats a message and sends ONE IPC message to
        // the Layer 1 physical driver task. That's the only IPC cost.
        let raw = flint::bus::transfer(&self.bus, &[0xFA, 0x00, 0x00])?;
        Ok(compensate_temperature(raw))
    }

    pub fn init(&self) -> Result<(), DriverError> {
        flint::bus::write(&self.bus, &[0xF4, 0x27])?;
        Ok(())
    }
}
```

**Adding a new bus type (1-Wire, CAN, I3C) — Layer 2:**
Write a library crate implementing the `flint::Bus` trait. Compiles into the calling context. One implementation, all devices on that bus work immediately.

**Adding a new MCU / board — Layer 1:**
Write a task crate implementing `flint::PhysicalBus`. This is the only layer that runs as an isolated task. Add the physical driver crate to `flint-arch-<target>`. All logical drivers and bus abstractions work immediately on the new hardware.

### Bus Abstraction Trait

```rust
pub trait Bus: Send + Sync {
    /// Full-duplex transfer. Returns received bytes.
    fn transfer(&self, tx: &[u8]) -> Result<FlintVec<u8>, BusError>;

    /// Write only. More efficient when response is not needed.
    fn write(&self, data: &[u8]) -> Result<(), BusError>;

    /// Read only (e.g. after setting a register address).
    fn read(&self, buf: &mut [u8]) -> Result<(), BusError>;

    /// Set bus clock speed. Not all buses support all speeds.
    fn set_speed(&self, speed: BusSpeed) -> Result<(), BusError>;

    /// Assert chip select / slave address (bus-specific meaning).
    fn select(&self) -> Result<(), BusError>;

    /// Deassert chip select / release bus.
    fn deselect(&self) -> Result<(), BusError>;
}
```

### Physical Bus Trait

```rust
pub trait PhysicalBus: Send + Sync {
    /// Initialize the hardware peripheral.
    fn init(&mut self, config: &BusConfig) -> Result<(), BusError>;

    /// Perform a raw hardware transfer via DMA or register-driven I/O.
    fn raw_transfer(&self, tx: &[u8], rx: &mut [u8]) -> Result<(), BusError>;

    /// Enable or disable the peripheral clock.
    fn set_enabled(&mut self, enabled: bool);
}
```

### Template Files — Self-Teaching by Design

The template source files are the entire documentation a developer needs. Every method stub explains what the method must do, what it must not do, and shows a one-line example of a correct implementation. A developer who has never written an RTOS driver reads the template once and knows exactly what to do.

**`drivers/logical/_template/src/lib.rs`:**

```rust
//! Flint Logical Driver Template
//!
//! A logical driver knows how to talk to a specific device (sensor, display,
//! radio, etc.). It knows nothing about which bus it's on or which MCU it's
//! running on — that is handled by the layers below.
//!
//! To create a new driver:
//!   1. Replace "MyDevice" with your device name throughout this file.
//!   2. Implement the methods below using only flint::bus::* calls.
//!   3. Add your device to board.rs under TARGET_DEVICES.
//!   4. Use it in your tasks via flint::bus::open("your_device_name").
//!
//! Rules:
//!   - Never import from flint::hal or any physical/bus driver crate.
//!   - Never call flint::task::sleep_ms() inside a driver method called
//!     frequently — prefer non-blocking reads with a ready/busy check.
//!   - Never panic. Return Result<_, DriverError> from fallible methods.

#![no_std]
use flint_api::{bus, BusHandle, DriverError};

pub struct MyDevice {
    bus: BusHandle,
}

impl MyDevice {
    /// Create a new instance. Called automatically by Flint at boot
    /// when this driver is listed in board.rs TARGET_DEVICES.
    /// `bus` is the handle for the bus this device is wired to.
    pub fn new(bus: BusHandle) -> Self {
        Self { bus }
    }

    /// Initialize the device. Called once at boot after new().
    /// Send any required startup commands or configuration here.
    /// Example: bus::write(&self.bus, &[REG_CONFIG, 0x27])
    pub fn init(&self) -> Result<(), DriverError> {
        // TODO: send init sequence
        Ok(())
    }

    /// Example read method. Replace with your device's actual reads.
    /// Keep method names clear and specific: read_temperature(), not read().
    /// Example: let raw = bus::transfer(&self.bus, &[REG_DATA | READ_FLAG, 0x00])?;
    pub fn read_value(&self) -> Result<u16, DriverError> {
        let raw = bus::transfer(&self.bus, &[0x00, 0x00])?;
        Ok(u16::from_be_bytes([raw[0], raw[1]]))
    }
}
```

```markdown
A logical driver is a Rust library crate that knows how to talk to one
```

### Community Driver Convention

Third-party drivers require zero infrastructure beyond what Cargo already provides.

**Naming convention:** `flint-driver-<devicename>` (e.g. `flint-driver-ina219`, `flint-driver-nrf24l01`)

**Community index:** A single file at `https://github.com/flint-rtos/drivers/blob/main/drivers.toml`:

```toml
# Community Flint driver index
# Submit a PR to add your driver. One line per driver.
# Format: name = { git = "url", description = "short description" }

[drivers]
ina219    = { git = "https://github.com/alice/flint-driver-ina219",    description = "INA219 current/power monitor (I2C)" }
nrf24l01  = { git = "https://github.com/bob/flint-driver-nrf24l01",   description = "nRF24L01+ 2.4GHz radio (SPI)" }
ds18b20   = { git = "https://github.com/carol/flint-driver-ds18b20",  description = "DS18B20 temperature sensor (1-Wire)" }
max7219   = { git = "https://github.com/dave/flint-driver-max7219",   description = "MAX7219 LED matrix driver (SPI)" }
```

The wizard reads this file during `cargo flint new-driver` to populate the device driver selection list. No registry server, no authentication, no infrastructure — just a PR to one file on GitHub.

**Git tag / SHA pinning is required** for all `drivers.toml` entries. Branch references are not permitted — they cause silent build breakage when a driver author pushes incompatible changes. Enforced as a CI check on the `flint-rtos/drivers` repo: PRs without a pinned ref are rejected automatically.

```toml
# Correct — pinned to a tag
ina219   = { git = "https://github.com/alice/flint-driver-ina219", tag = "v0.2.1", description = "INA219 current/power monitor (I2C)" }

# Also correct — pinned to a SHA
nrf24l01 = { git = "https://github.com/bob/flint-driver-nrf24l01", rev = "a3f1c9d", description = "nRF24L01+ 2.4GHz radio (SPI)" }

# Rejected by CI — branch reference is not stable
# ds18b20 = { git = "...", branch = "main", description = "..." }
```

**Future (Phase 10+):** When the community driver count warrants it, publish curated drivers to crates.io under the `flint-driver-` namespace. Cargo already handles version management, yanking, and search. The namespace convention is the only coordination required.

## First-Class Debugging & Instrumentation

Debugging is not an afterthought. It is a named build profile, a set of kernel-level primitives, and a defined protocol for getting data out of the device. All debug features are **zero-cost when disabled** — in release profile they compile to nothing.

### Debug Build Profiles

```toml
# Set by the wizard. Changeable by the developer at any time.

[profile.release]
# flint-debug = off
# All trace/metric macros → zero instructions
# Panic handler → minimal reset only
# Stack painting → off
# Binary: smallest possible

[profile.dev]
# flint-debug = level-1  (logging + metrics + postmortem)
# flint::log!() → UART or RTT output
# flint::metric::*() → static metrics table
# Panic handler → full postmortem capture + UART dump
# Stack painting → on (high-water mark tracking)
# Binary: moderate overhead

[profile.trace]
# flint-debug = level-2  (level-1 + kernel event tracing)
# Trace ring buffer active
# All kernel events timestamped: task switch, queue send/recv,
#   interrupt fire, DMA start/complete, MPU fault
# Readable live via shell or RTT
# Binary: larger, SRAM: +2-4KB for trace buffer

[profile.instrument]
# flint-debug = level-3  (level-2 + everything)
# ITM output on ARM (requires trace-capable debugger)
# Timing measurement macros active
# Per-task CPU utilization tracking
# Binary: largest, SRAM: +4-8KB
# Not for production. For deep timing/scheduling investigation.
```

The wizard asks: *"What debug level do you want for your development build?"* and configures the appropriate profile. The developer switches profiles with `cargo build --profile trace` — no other changes needed.

### `flint::log` — Structured Logging

Available from Level 1. Zero-cost in release.

```rust
flint::log::error!("motor fault: overcurrent on phase {}", phase);
flint::log::warn!("queue {} near full: {}/{}", name, depth, capacity);
flint::log::info!("sensor init complete, id=0x{:02X}", chip_id);
flint::log::debug!("raw ADC reading: {}", raw);
flint::log::trace!("SPI byte: 0x{:02X}", byte); // level 3 only
```

Output goes to the configured debug transport (UART, RTT, ITM — see below). Each message is prefixed with a timestamp in ticks and the calling task name:

```
[  1042ms][sensor_task ] INFO  sensor init complete, id=0x60
[  1043ms][consumer    ] WARN  queue sensor_queue near full: 15/16
```

The kernel ring buffer stores the last N log messages (configurable, default 32). Readable via `flint> dmesg` in the shell or via the debug transport at any time.

### `flint::metric` — Named Counters & Gauges

Available from Level 1. Zero-cost in release.

```rust
// Define metrics statically — no heap allocation
static UART_RX_BYTES:   flint::Counter = flint::Counter::new("uart0.rx_bytes");
static SENSOR_Q_DEPTH:  flint::Gauge   = flint::Gauge::new("sensor_q.depth");
static ADC_SAMPLE_RATE: flint::Gauge   = flint::Gauge::new("adc.samples_per_sec");

// Update from anywhere — interrupt-safe, lock-free
UART_RX_BYTES.increment_by(n);
SENSOR_Q_DEPTH.set(queue_depth);
```

All metrics live in a fixed static table. The shell `flint> metrics` command dumps them live. Future: export over TCP/IP as JSON for external dashboards.

```
flint> metrics
NAME                     VALUE      TYPE
uart0.rx_bytes           18432      counter
uart0.tx_bytes           4096       counter
sensor_q.depth           3          gauge
adc.samples_per_sec      100        gauge
task.sensor.cpu_pct      4          gauge    (level-3 only)
task.consumer.cpu_pct    1          gauge    (level-3 only)
```

### `flint::trace` — Kernel Event Tracing

Available from Level 2. Zero-cost at Level 0 and 1.

A lockless ring buffer in a reserved SRAM region. Written from any context including interrupts. Never blocks. Overwrites oldest entries when full.

Kernel-emitted events (automatic, no user code required):

```
[  1000ms] TASK_SWITCH    from=sensor_task(id=2) to=consumer(id=3)
[  1000ms] QUEUE_SEND     queue=sensor_q depth=4/16 task=sensor_task
[  1000ms] TASK_SWITCH    from=consumer(id=3) to=idle(id=0)
[  1001ms] IRQ_FIRE       irq=3 (uart0_rx)
[  1001ms] QUEUE_SEND     queue=uart_rx depth=1/8 from=irq
[  1001ms] TASK_UNBLOCK   task=uart_reader(id=4) reason=queue_recv
[  1001ms] TASK_SWITCH    from=idle(id=0) to=uart_reader(id=4)
[  1001ms] DMA_START      peripheral=uart0 handle=0x3F dir=rx bytes=32
[  1002ms] DMA_COMPLETE   handle=0x3F bytes=32
```

User code can emit custom trace events:

```rust
flint::trace!(FlintEvent::User { tag: "motor_start", value: rpm });
```

Readable via `flint> trace` in the shell, or streamed live over RTT.

### `flint::panic` — Postmortem Capture

Always enabled in non-release builds. In release builds, configurable between minimal-reset and full-capture.

When any task panics or a hard fault occurs:

1. Immediately disable preemption (not interrupts — debug exceptions must stay enabled)
2. Capture full snapshot into the panic SRAM region:
   - Faulting task name, ID, priority
   - Full register state at fault
   - Stack trace (best-effort, limited by no-MMU frame walking)
   - Last 32 trace events (if Level 2+)
   - Last 32 log messages
   - All metric values at time of fault
   - Tick count and uptime
3. Write snapshot to `/fs/panic.log` if filesystem is available
4. Dump human-readable postmortem to debug UART / RTT:

```
╔══════════════════════════════════════════════════════╗
║              FLINT PANIC — POSTMORTEM                ║
╚══════════════════════════════════════════════════════╝
Uptime:      4823ms (tick 4823)
Task:        sensor_task (id=2, priority=Normal)
Cause:       stack overflow

Register state:
  PC=0x400D1A2C  SP=0x3FFB0000  PS=0x00060033
  A0=0x400D1A20  A1=0x3FFB0000  A2=0x00000000

Stack high-water: 2048/2048 bytes used (OVERFLOW)

Last log messages:
  [4820ms][sensor_task] INFO  reading sensor
  [4821ms][sensor_task] DEBUG entering compensation fn
  [4822ms][sensor_task] DEBUG recursive call depth=47   ← likely cause

Last trace events:
  [4822ms] TASK_SWITCH  from=consumer to=sensor_task
  [4822ms] QUEUE_RECV   queue=cmd_q sensor_task
  [4823ms] STACK_WARN   task=sensor_task used=1900/2048
```

The panic region in SRAM survives soft reset. On reboot, Flint checks if a panic snapshot is present and logs a warning before resuming normal operation:

```
[  0000ms][kernel      ] WARN  previous session ended in panic — run 'flint> panic' to view
```

### Stack Painting

Always enabled. Zero meaningful overhead.

Every task stack is filled with `0xDEADBEEF` at spawn time. The scheduler checks the high-water mark on every context switch by scanning from the stack bottom for the first non-`0xDEADBEEF` word. Result stored in the task descriptor and visible via `flint> tasks`:

```
flint> tasks
NAME          ID  PRI   STATE    STACK USED  STACK MAX  HWM%
sensor_task   2   Norm  Running  1024        2048       50%
consumer      3   Norm  Blocked  256         4096       6%
nsh           5   Bkgd  Running  512         8192       6%
idle          0   Bkgd  Ready    64          512        12%
```

A stack usage warning fires via `flint::log::warn!` when any task exceeds 80% high-water mark.

### Debug Transports

Flint selects the best available transport at build time based on board and debug level. No manual configuration required — the wizard handles it.

| Transport | Availability | Speed | Notes |
|---|---|---|---|
| UART | Always | Slow | Default console + debug output |
| RTT (SEGGER) | JTAG connected | Fast | No UART needed. Works with `probe-rs`. Preferred when debugger attached. |
| ITM | ARM Cortex-M only | Very fast | Dedicated trace pins. Requires trace-capable debugger. Level 3 only. |
| Semihosting | QEMU / emulator | N/A | Useful for host-side testing. Never use on real hardware. |
| Flash postmortem | Always (Phase 9+) | N/A | Panic dump to `/fs/panic.log`. |

Multiple transports can be active simultaneously (e.g. UART for shell, RTT for trace stream).

### `CriticalSection`

A named primitive in `flint-hal`. Architecture implementations provide a token-based critical section that masks interrupts up to a configurable priority threshold — it does not disable all interrupts, which would break real-time properties.

```rust
pub trait CriticalSection {
    /// Enter a critical section. Returns a token that restores interrupt
    /// state when dropped. Masks interrupts up to CRITICAL_SECTION_PRIORITY.
    /// On AMP Core 0: masks local interrupts only — no cross-core locking needed.
    fn enter() -> CriticalSectionToken;
}

// Usage — interrupt-safe, priority-respecting
let _token = flint::cs::enter(); // interrupts masked for this scope
MY_SHARED_STRUCT.update();
// _token dropped here — interrupts restored automatically
```

The lockless trace ring buffer, the scheduler ready queue, and all kernel data structures use `CriticalSection` rather than ad-hoc interrupt disable/enable pairs. This makes the critical section boundary explicit, auditable, and portable across architectures.

### `RawStorage`

Defined alongside `BlockDevice` in `flint-hal`. Handles byte-addressable non-block storage: EEPROM, FRAM, battery-backed SRAM. These devices must not go through the `BlockDevice` / LittleFS path because: (a) they have no erase-before-write requirement, (b) EEPROM has low write endurance (~1M cycles) that LittleFS wear leveling cannot help with, and (c) FRAM has essentially unlimited endurance and wastes cycles going through a block abstraction.

```rust
pub trait RawStorage {
    /// Read `len` bytes starting at `addr`.
    fn read(&self, addr: u32, buf: &mut [u8]) -> Result<(), StorageError>;

    /// Write `buf` starting at `addr`. No erase required.
    fn write(&mut self, addr: u32, data: &[u8]) -> Result<(), StorageError>;

    /// Total addressable bytes.
    fn capacity(&self) -> u32;

    /// Endurance hint in write cycles per byte. Used for wear warnings.
    /// EEPROM: ~1_000_000. FRAM: u32::MAX (effectively unlimited).
    fn endurance_hint(&self) -> u32;
}
```

Exposed to applications via `flint::eeprom::read/write` and `flint::fram::read/write`. Visible in the shell as `/dev/eeprom0`, `/dev/fram0` etc.

### `BlockDevice`
```rust
pub trait BlockDevice {
    const BLOCK_SIZE: usize;
    fn read(&self, block: u32, buf: &mut [u8])  -> Result<(), StorageError>;
    fn write(&mut self, block: u32, buf: &[u8]) -> Result<(), StorageError>;
    fn erase(&mut self, block: u32)             -> Result<(), StorageError>;
    fn block_count(&self) -> u32;
}
```
Defined now. Stable forever. Future: async variants for NVMe/PCIe, `trim()` hint for SSDs.  
**EEPROM / FRAM exception:** byte-addressable storage (EEPROM, FRAM, battery-backed SRAM) never goes through `BlockDevice` or LittleFS. Use the `RawStorage` trait. Exposed as `flint::eeprom::*` / `flint::fram::*` and `/dev/eeprom0` / `/dev/fram0` in the shell.

## Phase-by-Phase Development Matrix

### Phase 0 — Xtensa Exception, Context & Tick Model

**Goal:** Exception handling, context save/restore, and timer interrupt correct under register window pressure before any scheduler exists.

**Mechanics:**
- Exception vector table (`vectors.S`): `WindowOverflow4/8/12`, `WindowUnderflow4/8/12`.
- `save_context` / `restore_context`: all windowed registers, `SAR`, `LBEG/LEND/LCOUNT`, `PS`.

**Syscall entry — critical Xtensa specifics:**
The `syscall` instruction is the correct entry point. However, because Layer 3 and Layer 2 execute in the application task context using normal windowed Xtensa calls, the call stack may be several windows deep by the time the syscall fires. The assembly stub must:
1. **Force a window spill first** — execute a `spill_registers` equivalent that flushes all live register windows to the user-space stack *before* any non-windowed save. This prevents a window overflow exception from triggering inside the kernel syscall router, which would cause an unrecoverable double-exception.
2. Immediately use **non-windowed load/store instructions** (`l32i`/`s32i`) to dump the active physical register window directly into the target `TaskContext` struct
3. **Never use `entry`/`retw` calling conventions** inside the core syscall router — these trigger further window rotation which corrupts saved state
4. Disable window overflow exception handling for the duration of the syscall handler so that a near-full user stack cannot trigger a recursive double-exception
5. Restore window state explicitly on return via `restore_context` before `rfe`

This means the inner syscall router in `flint-arch-xtensa` is written in a mix of assembly and `#[naked]` Rust functions. No standard Rust function calls until window state is fully saved.

- Timer interrupt entry: same window-freeze requirement applies — force window spill, then non-windowed save, before any Rust code runs.
- Satisfy `SyscallABI` and `TickSource` traits for Xtensa.
- Panic SRAM region: reserved in linker script. Survives soft reset. No content yet.
- Stack painting: `0xDEADBEEF` fill implemented in `task_spawn` stub.

**Deliverable:** Two standalone tests: (a) syscall under active register window pressure — arguments arrive uncorrupted across multiple nested call depths. (b) Timer interrupt fires during a windowed function call — full context saved and restored, execution resumes correctly. Both must pass before Phase 1 begins.

---

### Phase 1 — Preemptive Scheduler, Queues & Debug Level 1

**Goal:** Multiple preemptive tasks. Typed message queues. Logging and metrics active.

**Mechanics:**
- Hardware timer tick drives preemption. Default 1ms. Configurable via `TICK_PERIOD_US`.
- Priority scheduler: highest ready task runs. Round-robin within band at 10ms quantum.
- Priority inheritance on `flint::Mutex` from day one.
- `flint::Queue<T, N>` — statically allocated, bounded, typed. Send/recv with timeout.
- `flint::task::spawn`, `sleep_ms`, `yield_now`, `current_id`, `current_name`.
- Stack painting at spawn. High-water mark check on every context switch.
- **Debug Level 1 active from this phase:** `flint::log`, `flint::metric`, `flint::panic` postmortem handler.
- Kernel ring buffer (2KB default) in SRAM. `dmesg` readable immediately.

**Deliverable:** Three tasks at different priorities demonstrating preemption. Typed queue passing messages. Stack high-water visible. `flint::log::info!` output on UART. Panic handler fires correctly on a deliberately induced stack overflow and prints a readable postmortem.

---

### Phase 2 — MPU Isolation & Interrupt Routing

**Goal:** Memory isolation between tasks. Hardware interrupts routed safely to driver tasks.

**Mechanics:**
- `MpuManager` for Xtensa. Regions configured on every context switch.

- MPU region audit document produced as a deliverable.
- `panic` snapshot now captures MPU region state at time of fault.

**Deliverable:** GPIO driver blocks on queue recv, wakes on button press. Unauthorized register access faults correctly. MPU audit document complete. Panic postmortem includes MPU state.

### Phase 3 — DMA Broker

**Goal:** Driver tasks use DMA without programming the DMA engine directly.

```rust
flint::dma::alloc(size) → DmaHandle
flint::dma::submit(handle, direction, peripheral_id) → TransferId
flint::dma::await(transfer_id) → Result
```

- `dma_alloc`: carves sub-region from SRAM DMA pool. The MPU is updated to grant the requesting driver **read/write access to the data region** of this sub-region so it can fill or drain the buffer. The driver never has access to the DMA engine's configuration registers.
- `dma_submit`: the driver passes a handle and a length. The kernel:
  1. Validates the handle belongs to the calling task
  2. Validates `peripheral_id` matches the task's allowed peripherals from the board manifest
  3. Validates the transfer length does not exceed the allocated sub-region
  4. **Writes the DMA source/destination address registers directly** — the driver never touches these registers
  5. Arms and starts the DMA engine from kernel space
  6. Returns a `TransferId` immediately
- `dma_await`: blocks calling task. DMA completion interrupt → kernel sends wakeup to task queue.
- Descriptor rings: single `dma_submit` with `RING` flag. Kernel programs all descriptors upfront.

**The race condition that does not exist in this model:** a driver cannot modify the DMA destination pointer after validation because it has no access to the peripheral's DMA address registers at any point. The MPU grants the driver access to the *data buffer*, not to the *DMA engine registers*. These are distinct memory regions. The kernel owns the configuration registers exclusively.

- Debug: `flint::trace!` emits `DMA_START` and `DMA_COMPLETE` events at Level 2.
- Metrics: DMA throughput automatically tracked per peripheral.

**Deliverable:** SPI driver performs DMA transfer without touching DMA registers. Cross-region DMA attempt rejected. DMA events visible in trace output.

## High-Risk Items & Mitigations

| Risk | Mitigation |
|---|---|
| Xtensa register windowing corrupts syscall or interrupt context | Phase 0 dedicated entirely to this. Standalone stress tests for both paths. Nothing else built until both pass. |
| Preemption during kernel data structure access | Short critical sections (interrupt disable only — never disable debug exceptions). Max critical section length documented. |
| MPU region budget exhausted (8 regions, ESP32) | Audited Phase 2. One driver mapped per time slice. Documented constraint. |
| DMA bypasses MPU | DMA broker validates all submissions. Drivers never touch DMA registers. |
| Flash XIP cache miss causes interrupt latency | All ISRs + tick handler in IRAM. Enforced by `#[link_section]`. Reviewed in MPU audit. |
| HAL abstraction leaks Xtensa assumptions | Phase 8 ARM port is the validation test. Any kernel core change required = abstraction failure, must fix. |
| Priority inversion on shared resources | Priority inheritance on all `flint::Mutex` from Phase 1. Mandatory, not optional. |
| Trace ring buffer write causes interrupt latency | Lockless ring buffer. Single atomic index increment. Measured and bounded in Phase 3. |
| Debug overhead leaks into release builds | Verified by inspecting release binary with `cargo bloat`. Zero tolerance for debug symbols or branches in release profile. |
| Layer 3 logical driver accidentally accesses hardware | Enforced structurally: Layer 3 crates cannot import `flint-arch-*` or Layer 1 crates. The Cargo dependency graph makes this a compile error, not a convention. |
| Three-layer model introduces multi-hop IPC latency | Resolved: Layer 3 and Layer 2 are library crates compiled into the calling context. Exactly one IPC hop per hardware operation (to the Layer 1 physical driver task). Same cost as FreeRTOS with a driver abstraction. |
| SMP locking complexity on dual-core ESP32 | Resolved: AMP model. Core 0 owns kernel + drivers. Core 1 disabled or single app thread. IPI + crossing queue for inter-core messaging. SMP is a named future phase. |
| Xtensa double-exception from window overflow during syscall | Resolved in Phase 0: window spill forced before non-windowed save. Window overflow disabled during handler. No `entry`/`retw` in syscall router. |
| Deep call stack causes window overflow inside kernel syscall router | Resolved: `spill_registers` step at syscall entry flushes all live windows to user stack before kernel takes control. Tested under maximum call depth in Phase 0 stress test. |
| PSRAM cache miss destroys real-time determinism for critical tasks | Wizard enforces `Critical` and `Normal` priority task stacks to internal SRAM by default. Warns explicitly if developer manually places a real-time task in PSRAM. |
| AMP crossing queue reads stale cached data on Core 0 | Crossing queue mapped to uncached memory region in linker script, OR explicit cache writeback (Core 1 before enqueue) and invalidate (Core 0 before dequeue) on every inter-core handoff. Non-negotiable, implemented from first inter-core message. |
| Community driver breaks builds on `drivers.toml` `main` branch reference | CI check on `flint-rtos/drivers` repo rejects PRs without pinned tag or SHA. Enforced before merge, not after. |
| User driver template becomes outdated as API evolves | Template `lib.rs` stubs are generated from the same source as the Flint API crate. A `cargo flint check-drivers` command warns when local driver templates are out of sync with the installed Flint version. |
| Community driver pulls in unsafe hardware assumptions | Logical drivers that try to import `flint::hal::*` fail to compile — the Cargo dependency graph enforces the layer boundary. Community drivers cannot bypass this. |
| Wizard generates broken project for edge-case board config | Acceptance test: run by a developer unfamiliar with Flint. `cargo run` must succeed on real hardware with zero manual steps. |

## Open Decisions (Resolve Before Coding Begins)

1. **Dual-core (ESP32) — resolved as AMP:** Flint uses Asymmetric Multiprocessing for dual-core targets. Core 0 runs the kernel, all driver tasks, and OS services. Core 1 is either disabled or dedicated to a single high-speed application thread. True SMP on a no-MMU dual-core system requires cross-core atomic primitives, hardware MUTEX registers, and locking on every shared kernel data structure — complexity that violates the "simpler than Zephyr" goal. AMP is honest, fast, and simple to reason about. Inter-core communication uses a dedicated Inter-Processor Interrupt (IPI) mechanism and a crossing queue. Core 1 is reserved in the memory map from Phase 0. SMP is a named future phase, not a default.

   **Cache coherency requirement for the crossing queue:** The ESP32's two cores have independent data caches with no hardware coherency between them. The AMP crossing queue must be mapped to an **uncached memory region** in the linker script, or both sides of every inter-core handoff must execute explicit cache writeback (Core 1 before enqueue) and cache invalidate (Core 0 before dequeue) instructions. Failure to handle this means Core 0 reads stale cached data after Core 1 writes. This is not optional and not a future concern — it must be designed into the crossing queue implementation from the first inter-core message.

2. **Kernel ring buffer size:** Recommend 2KB in SRAM for Level 1, additional 4KB trace buffer for Level 2. Both configurable in `board.rs`.

3. **Minimum SRAM floor:** Recommend 256KB. Document as minimum in `porting_guide.md`.

4. **Async executor placement:** Recommend pure library executor in `api/` first. Kernel-assisted wakers as a later optimization. Does not block any phase.

5. **`cargo run` tooling:** Recommend `probe-rs` as primary flash runner (supports ESP32 via JTAG + STM32 via SWD). `espflash` as ESP32-specific fallback for users without a JTAG probe. Wizard detects which is available.

6. **Community driver index:** The `flint-rtos/drivers` GitHub repo hosts `drivers.toml` — a flat list of community driver crates. Submitting a driver = one-line PR. The wizard reads this file to populate the `cargo flint new-driver` selection list. No registry server required for v1. When driver count warrants it, publish curated drivers to crates.io under the `flint-driver-` namespace convention — Cargo handles versioning and search from that point forward. Recommend establishing the naming convention and the `drivers.toml` index file before Phase 5 ships so early adopters follow the same pattern.
